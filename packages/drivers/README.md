# Database driver packages

Each database implementation belongs in its own workspace package with its own manifest and runtime dependencies. `api/` contains the shared driver contract and registry. `sqlite/` implements the first driver using Node's built-in `node:sqlite`, with one child process per connection so queries are asynchronous to the extension host and cancellable even inside native SQLite execution.

Drivers declare their database family, query languages, and capabilities. Optional metadata resources populate the native Connections tree, and optional table browsing returns bounded pages. Keep database connections in the extension host. Any future native dependency must support both local Electron and remote Node.js runtimes.

The SQLite process entry is bundled separately by `apps/extension/esbuild.mjs`. The driver client receives that installed entry's absolute path. Values are converted to JSON-safe transport types in the database process before crossing IPC or webview boundaries. Tests use real temporary databases and a real database process, including cancellation and transaction rollback.

`sql/` contains the shared relational adapter, explicit-session JavaScript transports (`pg`, shared MIT `mysql2` for MySQL/MariaDB, direct `tedious`, `@clickhouse/client`, and `oracledb` Thin), and optional worker entry points. `bun run build:drivers` builds one self-contained `.cjs` per engine into `dist/drivers`, plus release-pinned catalog metadata and license notices. The local extension release ships the catalog, notices, and all eleven optional worker bundles for automatic offline setup. Only selected workers are copied into the verified cache and started. A user-configured HTTPS base URL enables automatic downloads instead, allowing future hosted releases to omit bundled workers. Do not edit downloaded bundles or run npm in the installed extension directory. The core verifies each artifact before starting it as a child process; a worker is trusted executable code, not a security sandbox.

For public distribution, publish matching artifacts and their required license/source material together. MariaDB's LGPL connector requires preserving its applicable terms, source and replacement/relink rights; MIT/Apache transitive notices also remain applicable. No public endpoint or Marketplace publishing is configured by this local build.

Use `bun run test:drivers` for real PostgreSQL, MySQL, MariaDB and SQL Server conformance. `bun run test:drivers:native` also runs the isolated native VS Code credential/driver-install flow. See the root README for prerequisites and deliberate limitations.

`nosql/` uses the official MongoDB and Redis JavaScript clients behind the shared process transport. It exposes document/key pages and optimistic single-record changes separately from SQL table operations. Use `bun run test:nosql` and `bun run test:nosql:native` for real services and native wizard/browsing checks. TLS uses system CAs; Redis hash edits require Redis 7+ ACL preflight support.

The node-redis 6.3.0 npm workspaces omit the monorepo root license file. The unmodified license in `nosql/notices/node-redis-6.3.0.LICENSE` comes from the pinned [upstream release](https://github.com/redis/node-redis/blob/redis%406.3.0/LICENSE) and is included in the Redis artifact notices.

`duckdb/` adds the official pinned `@duckdb/node-api` 1.5.6-r.2 client behind the shared SQL worker transport. Its build plugin replaces the native binding loader with a worker-relative `native/duckdb.node` load; native code never enters the extension-host bundle. The shipped `duckdb/native-catalog.json` pins platform archive URLs, SHA-512 integrity, sizes, and SHA-256 hashes of the native addon, shared library, and upstream license. Only the matching platform archive is fetched on first use. Keep the API dependency and all catalog artifacts on the same exact release when upgrading. `DuckDbNativeInstaller` downloads, verifies, stages, and checks cached native files. The worker's JavaScript and MIT notices are bundled; the larger native package is optional. Native packages require HTTPS access to registry.npmjs.org once, then work offline.

DuckDB reuses bounded SQL capture, browsing, filters, export and catalog models; writable primary-keyed tables support reviewed, transactional grid writes. Open SQL transactions must be finished before a grid batch (no nested savepoints). Metadata covers the current catalog, and SQL can query attached/temp objects. Transaction state compares two standalone current_transaction_id() probes; explicit transactions keep the same ID. Real worker tests are part of `bun run test`, including exact values, CSV/Parquet, foreign keys, read-only files, optimistic edit rollback, transaction rollback, and cancellation. `DATSUMI_TEST_HEADLESS=1 bun run test:integration` additionally exercises the real native download and VS Code commands.

ClickHouse and Oracle use the SQL adapter with engine-specific transport, catalog and paging SQL. Oracle supports reviewed keyed-table edits with explicit commit/rollback semantics. ClickHouse grids remain read-only and transactions are unsupported. Neon/Supabase are connection presets for the existing PostgreSQL worker. Cloud integration settings remain outside the driver transport.
